# Как устроена работа над проектом

Версия 0.2.

Проект учебный, команда — симуляция. Я системный аналитик, остальные роли выполняют ИИ-агенты. Так я прохожу полный цикл аналитики — от исследования до приёмки MVP — с ревью на каждом шаге.

| Роль | Кто | Что делает |
|---|---|---|
| Системный аналитик | я | Доменные правила из опыта гида, интервью, решения, ревью черновиков, приёмка |
| Аналитик-помощник | ИИ (Claude) | Черновики артефактов по моим вводным |
| Заказчик | ИИ-агент с персоной владельца экскурсионной службы | Приоритеты, изменения по ходу проекта |
| Ревьюер требований | ИИ, скиллы `/sar` и `/sar-crosscheck` в отдельном чате | Независимое ревью требований и контрактов |
| Архитектор | ИИ-агент | Ревью решений и НФТ |
| Разработчик | ИИ-агент (Claude Code) | MVP по утверждённой спецификации, вопросы аналитику в issues |
| QA | ИИ-агент | Тест-кейсы по критериям приёмки |

Решения принимаю я. Черновик становится частью проекта после моего ревью. Заказчик-агент подтверждает продуктовые решения внутри симуляции. Ключевые решения и открытые вопросы Q-01–Q-05 я несу в реальную службу: что подтвердила она, а что только агент, видно по статусу в [журнале решений](decisions/decision-log.md).

## Где мои решения, а где черновик

Черновики пишет ИИ по моим вводным, поэтому важно видеть, что решал я. Примеры из истории проекта:
- **D-07.** В черновике v0.1 отписка уходила по SMS. Я заменил на мессенджер клиента: служба так работает, клиенты пишут в Telegram, реже в WhatsApp.
- **D-08.** В черновике v0.1 телефон гида клиенту не передавался. Я вернул его: клиенты регулярно звонят гиду уточнить, куда идти, и добавил согласие гида.
- **D-03 → D-11.** Правило «кто первым откликнулся» было моим допущением из практики. Интервью его опровергли, и я заменил его окном откликов.
- **Ревью итерации 2.** Что из замечаний я принял, что принял с изменениями и с чем не согласился — в комментариях PR с исправлениями.

## Цикл одной истории

1. Заказчик приносит запрос — заводится issue.
2. Встреча с заказчиком, протокол, история с критериями приёмки.
3. Спецификация в отдельной ветке и PR.
4. Ревью: `/sar`, архитектор, `/sar-crosscheck`. Замечания — комментариями в PR или задачами по шаблону «Замечание ревью», ответы и правки там же.
5. CI проверяет модель данных, контракт API, схемы BPMN и ссылки. Без зелёного CI изменения не попадают в `main`.
6. Merge, карточка переходит в Ready for Dev, разработчик собирает. Если в спецификации дыра, он не додумывает, а заводит issue «Вопрос аналитику».
7. QA проверяет, я принимаю по критериям и размечаю дефекты: ошибка кода или ошибка требований.
8. В конце итерации — демо заказчику и ретро.

Итерации 1–2 я вёл напрямую в `main`, это видно по истории коммитов. По этому циклу работа идёт с исправлений по ревью: первый PR — версия 0.4.

GitHub Projects, колонки: Backlog → Analysis → Review → Ready for Dev → In Dev → Testing → Done. Шаблоны задач лежат в `.github/ISSUE_TEMPLATE`, в `main` изменения попадают только через PR с зелёным CI.
