# amoCRM

CRM службы и источник данных заявки (D-04). Контракт сверен с официальной документацией amoCRM: [формат вебхуков](https://www.amocrm.ru/developers/content/crm_platform/webhooks-format), [управление вебхуками](https://www.amocrm.ru/developers/content/crm_platform/webhooks-api).

## Как диспетчер узнаёт о заявках

- Вебхук на события сделок: `add_lead`, `update_lead`, `status_lead`, `delete_lead`, `restore_lead`. Один вебхук подписывается на несколько событий, в аккаунте их может быть не больше 100.
- Вебхук настраивается в интерфейсе amoCRM. Через API (`POST /api/v4/webhooks`) — только на расширенном и профессиональном тарифах.
- **Вебхук — сигнал, а не данные** ([ADR-001](../decisions/adr/ADR-001-webhook-as-signal.md)). Получив его, диспетчер запрашивает актуальную сделку через API и работает с ней. Поэтому неполный, повторный или поддельный вебхук не испортит данные.
- Если вебхук не дошёл, раз в 15 мин сверка запрашивает сделки, изменённые с момента последней успешной сверки минус 5 минут (NFR-06). После простоя диспетчера первая сверка догружает весь пропуск.
- События одной сделки обрабатываются строго по очереди: следующее берётся, когда предыдущее применено. Поэтому при равном `updated_at` (время в amoCRM — целые секунды) более поздний ответ API не старее сохранённого, и правка в ту же секунду не теряется ([ADR-001](../decisions/adr/ADR-001-webhook-as-signal.md)).

## Приём вебхука

`POST /integrations/amocrm/webhook/{secret}` — контракт в [OpenAPI](../api/openapi.yaml).

| Свойство amoCRM | Что из этого следует |
|---|---|
| Тело — `x-www-form-urlencoded` вида `leads[update][0][id]=7551167`, при удалении — `leads[delete][0][id]=…` | Сохраняем тело как есть в `inbound_event`, разбираем асинхронно |
| amoCRM ждёт ответ не больше 2 с, иначе считает вебхук недоставленным | Отвечаем 200 сразу после сохранения |
| Повторы: через 5 мин, потом через 15 мин; ещё две попытки, через 15 мин и через 1 ч, — только если мы ответили 499 или 5xx | Дубли отсекает ключ дедупликации |
| Если за 2 ч больше 100 невалидных ответов и последний тоже невалидный, вебхук отключается | Отвечаем 200 даже на событие, которое не обрабатываем. Алерт, если в рабочее время от amoCRM ничего не приходит дольше обычного |
| Идентификатора события нет | Ключ дедупликации — `amocrm:lead:<id>:<action>:<last_modified>` |
| Подписи нет | Секрет в адресе вебхука и проверка `account[subdomain]`. Данные всё равно берутся из API |

## API

| Запрос | Зачем |
|---|---|
| `GET /api/v4/leads/{id}?with=contacts` | Актуальная сделка и связанный контакт |
| `GET /api/v4/contacts/{id}` | Имя и телефон клиента |
| `GET /api/v4/leads?filter[updated_at][from]=<unix>` | Сверка: что изменилось с момента последней успешной сверки |
| `GET /api/v4/leads/custom_fields` | Один раз при настройке: идентификаторы полей сделки |

Авторизация — OAuth 2.0 приватной интеграции, токены хранятся в секретах. На 401 токен обновляется и запрос повторяется один раз, на 429 — пауза.

## Маппинг сделки

Идентификаторы дополнительных полей у каждого аккаунта свои: их выдаёт `GET /api/v4/leads/custom_fields` или интегратор, который настраивал CRM.

| amoCRM | Поле диспетчера | Правило |
|---|---|---|
| `id` | `booking.external_id` | — |
| `updated_at` | `booking.external_updated_at` | Старое состояние не перетирает новое, равное время с другими данными применяется (NFR-04) |
| `status_id` | `booking.status`, `booking.cancel_reason` | Этап «Отменена» → CANCELLED с причиной CRM_CANCELLED, «Проведена» → COMPLETED (BR-36). Идентификаторы этапов — у интегратора |
| Поле «Дата и время экскурсии» | `starts_at` | Unix-время, показываем по Москве |
| Поле «Маршрут» | `route_id` | По справочнику маршрутов. Не нашли — заявка в «Требует внимания» (US-01) |
| Поля «Взрослые», «Дети», «Льготные» | `adults`, `children`, `discounted` | Сумма не меньше 1. **Этих полей в CRM сейчас нет**: в AS-IS у сделки одно поле «Число участников». Интегратор добавляет их до релиза 1 (A6). Переходное правило: «Число участников» → `adults`, ожидаемая сумма — из `price` сделки, а если его нет, заявка в «Требует внимания» (F-07) |
| Поле «Оплата» | `payment_method` | Наличные или перевод |
| Поле «Мессенджер» | `client.messenger` | Поля тоже нет, его добавляет интегратор. Пусто — Telegram: у 90% клиентов отписка уходит туда, администратор меняет канал при отправке |
| `price` | `expected_amount` | 0 — считаем по тарифу (BR-32); тарифа нет — «Требует внимания» |
| Контакт: имя, телефон (поле с кодом `PHONE`) | `client.full_name`, `client.phone_e164` | Телефон приводим к E.164: `8XXXXXXXXXX` → `+7XXXXXXXXXX`, иностранные номера — как есть, с `+` (F-30) |

## Отказы

| Ситуация | Что делаем |
|---|---|
| API amoCRM не отвечает при разборе события | Событие остаётся необработанным, повтор через 1, 5 и 15 мин, затем алерт |
| У сделки нет обязательного поля | Заявка не создаётся, администратор видит её в «Требует внимания» с перечнем полей |
| Вебхуки перестали приходить | Сверка подхватывает изменения, алерт администратору службы |
| Сделку удалили | Как отмена с причиной CRM_DELETED: группы отменяются, гиды получают уведомление (BR-20) |
| Сделку восстановили (`restore_lead`) после удаления или отмены | Заявка снова ACTIVE, для неё создаются новые группы и начинается поиск. Отменённые группы остаются в истории. Если заявку отменили в панели аварийно (BR-04), восстановление не применяется само, а попадает в «Требует внимания» |
| amoCRM недоступна, а заявку нужно отменить | Аварийная отмена в панели, заявка помечается «Повторить в amoCRM» (BR-04) |
