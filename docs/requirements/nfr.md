# Нефункциональные требования

Версия 0.3. Целевые значения — предложение, объёмы уточняются после интервью. Для каждого требования указано, что именно измеряем и где.

| ID | Требование | Как измеряем |
|---|---|---|
| NFR-01 | Предложение уходит всем подходящим гидам не позже чем через 60 с после создания группы или наступления времени рассылки | От записи группы в базе до успешного ответа Telegram Bot API на отправку последнему гиду. Доставку на телефон гида Telegram не сообщает, поэтому это ближайшая наблюдаемая точка. 95% случаев за месяц |
| NFR-02 | Плановые сообщения гидам (сводки, запросы подтверждения) уходят, а задачи на отписку появляются у администратора не позже чем через 2 мин после планового времени с учётом тихих часов | От планового времени до успешного ответа Bot API или создания задачи. 99% за месяц |
| NFR-03 | Запланированные сообщения и эскалации не теряются при перезапуске или сбое | Расписание хранится в базе или в движке процессов, а не в памяти. Проверка: перезапуск сервиса во время теста, все плановые события отправлены |
| NFR-04 | Повторная доставка события из CRM не создаёт дублей групп и уведомлений. Событие с меньшей версией заявки не перезаписывает более новые данные | Тест с повтором и перестановкой событий |
| NFR-05 | Конкурентные действия над группой дают ровно один результат по [матрице](backlog.md#конкурентные-сценарии) | Тест: 20 одновременных нажатий «Взять группу» дают одно назначение и 19 ответов «Группу уже взял другой гид» |
| NFR-06 | Сверка с CRM каждые 15 мин по заявкам на ближайшие 7 дней догружает пропущенные изменения (при наличии API, Г6) | Тест: событие об изменении не отправлено, изменение появляется в диспетчере не позже чем через 15 мин |
| NFR-07 | Бот и планировщик доступны 99,5% времени с 07:00 до 22:00 по Москве. Плановые работы — в тихие часы | Внешняя проверка доступности раз в минуту, отчёт за месяц |
| NFR-08 | Сбои Telegram не теряют сообщения. Ошибка 429 — повтор после паузы, которую вернул Telegram в retry_after. Ошибка 403 «бот заблокирован» не повторяется и переводится в эскалацию (BR-31) | Тест с подменой ответов Bot API |
| NFR-09 | Входящие вызовы принимаются только от своих источников: вебхук Telegram — с секретным заголовком X-Telegram-Bot-Api-Secret-Token, вебхук CRM — с секретом или подписью CRM. Вход в панель — по учётной записи, сессия истекает после 12 ч бездействия | Тест: запрос без секрета получает отказ и записывается в журнал |
| NFR-10 | Персональные данные — по 152-ФЗ. Храним минимум: имя, телефон и мессенджер клиента; имя, телефон и Telegram ID гида. Телефон гида передаётся клиентам только с его согласия (BR-28). Базы на серверах в РФ. Телефон клиента обезличивается через P-20 (90 дней) после экскурсии. Доступ по ролям (BR-29) | Ревью схемы данных; тест доступа гида к чужой группе; проверка задания обезличивания |
| NFR-11 | Каждое изменение статуса группы, назначения и эскалации записывается в журнал: кто, когда, что было и что стало. Журнал хранится 1 год | Тест: после любого действия из бэклога в журнале появляется запись |
| NFR-12 | Время хранится в UTC, показывается по Москве (Europe/Moscow) | Тест на смену суток и тихие часы |
| NFR-13 | Любое действие гида — не больше двух нажатий от уведомления. Сообщение бота помещается на экран телефона без прокрутки, до 10 строк | Проверка макетов и приёмка на телефоне |
| NFR-14 | Параметры P-01…P-23 меняет администратор в панели без релиза. Исключения: время сводки P-06 задано в расписании, а максимум участников P-01 — жёсткое ограничение базы. Оба меняются релизом | Тест: изменение параметра применяется к новым группам без перезапуска |
| NFR-15 | Система выдерживает утроенную нагрузку пикового дня. Пик по исследованию — 12 заявок в день и 30 гидов, поэтому нагрузка мала, а узкое место — лимиты Telegram на рассылки | Нагрузочный тест: 40 заявок и 100 гидов за день |
