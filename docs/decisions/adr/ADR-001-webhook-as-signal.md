# ADR-001. Вебхук amoCRM — сигнал, данные — из API

Статус: принято. Связано с D-04, US-01, NFR-04, NFR-06.

## Контекст

Заявки живут в amoCRM, её настраивал внешний интегратор, своего программиста у службы нет. У вебхуков amoCRM нет идентификатора события и подписи. amoCRM ждёт ответ не дольше 2 секунд, повторяет недоставленное и отключает хук, если невалидных ответов слишком много.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Брать данные из тела вебхука | Нет лишних запросов | Тело неполное и повторяет структуру формы. Дубли и перестановки ломают данные. Поддельный запрос может их испортить |
| Опрашивать API по расписанию без вебхуков | Просто, всё под контролем | Задержка до интервала опроса, лишняя нагрузка на API |
| Вебхук как сигнал, данные из API, плюс сверка | Быстро и надёжно | Лишний запрос на каждое событие |

## Решение

Вебхук только сохраняется, ответ — сразу 200. Обработчик берёт сделку через `GET /api/v4/leads/{id}` и применяет её, если `updated_at` новее сохранённого. Раз в 15 минут сверка запрашивает сделки, изменённые за последний час.

## Последствия

- Дубли, перестановки и поддельные вебхуки не портят данные: правда — в API, порядок — по `updated_at` (проверено в [`ddl-checks.sql`](../../design/ddl-checks.sql)).
- Один запрос к API на событие. При 12 заявках в день это ничто.
- Если хук отключат, заявки всё равно придут через сверку, с задержкой до 15 минут, и сработает алерт.
